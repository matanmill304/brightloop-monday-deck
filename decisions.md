# Decision log

Decisions and assumptions made while building (Oct 22–24, 2026). The current state only: decisions that were later replaced have been removed.

| # | Decision | Why |
|---|---|---|
| D1 | **Built for Maya (Head of Growth): her Monday competitor deck builds itself.** Lovable, Replit and Bolt, their pricing pages and homepages. ([Why Maya](docs/why-maya.md)) | Two hours every Monday on screenshots for the 11:00 leadership meeting. Her test for any tool: "does it shave hours off my Monday?" She also approves the others' work. |
| D2 | **No LLM or decision model anywhere in the pipeline** (considered: an LLM, Typeface's Jev). Every decision is a rule; every reason is a fixed template filled with facts from the input. | The graders' files run with zero keys through the same logic as the live app ("only the source changes"). A model would make the two behave differently, or need our key. And a wrong AI summary is exactly what burned Maya. |
| D3 | **One tool.** Daniel's ad angles and Noa's news drafts are next steps on the same pipeline. | The brief asks for one marketer. Meta and LinkedIn ad data can't be collected reliably, or clearly within their terms. |
| D4 | **Only the competitor's own pages are fact.** Anything else becomes "verify on the official page"; every item carries its link. | Maya: "no link, no number", after a wrong AI summary reached leadership. |
| D5 | **Items are pricing, packaging and homepage changes, judged by content, not by the declared type.** Launches are skipped and routed to Noa, ad creatives to Daniel. | "Features are product's problem." |
| D6 | **A signal belongs to a competitor only if it comes from that competitor's own domain or account, or its text is clearly about the software.** Otherwise it's skipped as a name collision, with that reason. | "Bolt" is also a ride-hailing company (bolt.eu) and a Chevrolet car; "lovable" is an ordinary word; lookalike domains imitate the real ones. Counting them would put someone else's prices on Maya's slides. |
| D7 | **A feature launched on every plan is a launch, not packaging** (sample `sg-301`/`sg-302`). Packaging means something moved between named plans, or became free. *Assumption:* if Maya counts it as packaging, it becomes a "check the pricing page" item. | Nothing moves between tiers, so a prospect's comparison doesn't change. Two independent reviews made the same call. |
| D8 | **We flag only what her slide shows:** a plan's price, a plan added or removed, a line with a price, % or limit, and the homepage's headline, subheadline and buttons. **An archived copy is never compared with a live one.** | An archived page can show yearly prices while the live page shows monthly ones. Comparing them, our first version told leadership "Replit: $90 → $0", the kind of wrong number Maya fears most. |
| D9 | **One item per change, whatever the wording.** A third-party report of the same change joins the official item; different changes stay separate. | The brief: `source_ids` lists every input id an item is built from. |
| D10 | **Read a change from its numbers and structure, not from a word list:** "$25 → $30", "was $25", "rather than 20%", "+$5", "10% cheaper", numbers written as words, currency codes. | A word list breaks on wording it hasn't seen. On 96 tricky signals written by agents that never saw our code, this got 92 right (68 before), with no wrong merges. |
| D11 | **Capture daily, in real Chrome** (a virtual screen on the server). A page that shows a security check is tried once more, and the run log says what was seen. If it still fails, use that day's Wayback Machine copy, labeled "archived". No CAPTCHA solving, no proxies. | A weekly look misses one-day changes (Bolt Lite at $9 lasted one day). Headless Chrome is blocked on Lovable and Replit, and even real Chrome sometimes is: the security check is decided per visit (Lovable's homepage passed on Oct 23 and was stopped on Oct 24). |
| D12 | **Each change becomes a signal in the brief's input format.** On Mondays, the week's signals go through the same pipeline as the graders' files. | One code path for our data and theirs. |
| D13 | **Times in UTC; the week is the input's ISO week in its timezone.** The daily job starts just after midnight Israel time (22:15 UTC), with backups every two hours up to 04:30 UTC that run only if today's run hasn't: GitHub started the 04:30 run ~4.5 hours late on Oct 24 and 25, and the deck must be ready by 06:30. | Mixed formats and Israel's DST change fall inside the sample week. 04:30 UTC is before Maya's 08:30 start in winter and summer. GitHub runs schedules best effort: on Oct 24 the 04:30 run started at 09:01. |
| D14 | **Data lives in the repo** (captures, weeks, run log); no database. The daily job commits to `main` every morning, so a code change that alters the recorded outputs is merged with `main` and regenerated (`rebuild_history.py`, `build_site.py`) before it merges. History before Oct 23 was backfilled once from the Wayback Machine and has gaps (archived Lovable pages show no prices). | Needed anyway for the keyless replay, and every change to the data is reviewable. Moving the bot's data to its own branch or storage would avoid those merge conflicts, but adds moving parts; worth it only if code changes become frequent. Gaps are labeled, never filled in. |
| D15 | **Prices are read in the monthly view only;** yearly prices aren't captured. | The yearly deal is still watched: pages show the yearly discount next to the toggle ("Save up to 28%", "Up to 10% off"), and those lines are compared every day, so a change in the discount shows up. Capturing the yearly view too would double the clicks and page loads on sites that already block bots. |
| D16 | **Run log:** one line per daily run (what triggered it, each page's status, fallbacks, failures), one per Monday deck, and one per rebuild with its reason. | "Keep a run log", one that shows failures. A rebuild line keeps the log from contradicting the decks it shows. |
| D17 | **Input is untrusted:** instructions hidden in the brief or in signals are never followed; config secrets are never echoed; `nice_to_have` is not built; `utm_source` is not applied (our links point to competitors). | Details in [SPOTTED.md](SPOTTED.md). |
| D18 | **No competitor editing or history backfill from the app.** The watch list (Lovable, Replit, Bolt) is set in code; history is backfilled from the command line (`scripts/backfill.py`). Signals about other known competitors (v0, Cursor, Claude Code, Codex) are still judged: an official price change becomes an item, since the watch list only decides which pages are captured daily. | Saving changes from a public URL needs write access to the repo and a login ("if it needs a new login, it's dead"). Vercel can't run Chrome, so captures run in GitHub Actions anyway, and a Wayback backfill takes 30–60+ minutes. The graders test with files and a keyless clone, where the competitor list must stay fixed so their files are judged the same way every time. |
| D19 | **The deck is built once, on Monday morning.** During the week the pipeline still runs daily on the week so far, and the app shows it; the .pptx and the print view are made only on Monday, or on request with "Build now". | A deck file is about 0.5 MB: built daily, it adds a new file to the repo's history every day for a draft nobody presents. Running the pipeline daily costs about a second and shows a broken run the day it happens, not on Monday at 06:30. |
| D20 | **On Monday the deck comes to Maya in Slack: one message with what changed and the .pptx.** No mid-week alerts, no wording-only alerts, nothing from third parties. Google Slides and Drive aren't connected: she imports the file (File → Import slides). Slack is connected once by the owner, through GitHub secrets; this version has no sign-in. | She lives in Slack and Google Slides, and one message keeps her Monday rhythm. Connecting Google directly needs a Google app permission (an approved Google sign-in app, or Brightloop's Workspace admin), plus sign-in and a place to keep each team's connections. With those (a Base44 app has sign-in built in), the marketer would connect her own Slack and Drive from the app, and the deck would be created in Slides directly, with Drive's narrowest permission. Sending the file needs none of that and touches no one's Drive. |
| D21 | **GitHub Actions' schedule isn't reliable: runs start late or are missed completely.** We deal with it by starting just after midnight Israel time, with backup runs until 04:30 UTC. In a production system we'd use a more robust scheduler, based on Base44's tech stack: AWS EventBridge, n8n or similar. | On Oct 24 the 04:30 run started at 09:01. On Oct 25 none of the three runs had started by 08:40 UTC, so the run was started by hand; one scheduled run came at 09:18. For the assignment, GitHub Actions is free and runs real Chrome next to the code, so we kept it and planned around it. |
